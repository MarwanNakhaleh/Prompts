# Web Engineering Principles

These principles apply to every prompt in `web/` — build-app, feature-dev, set-up-hosting, refactoring, security, and QA. They are the background framework for every architecture, implementation, and audit decision.

When making decisions that depend on current framework behavior — caching semantics, rendering model, security controls, or any API — consult `web/resources.md` first. It lists the authoritative, regularly-updated source for each application slice so you ground decisions in live documentation rather than training-data memory.

## Simplicity is the deliverable
If two solutions work, ship the one that's easier to read and delete. Optimize for readability and the next engineer who maintains this. Unnecessary abstraction, premature generalization, speculative flexibility, and dependency bloat are bugs.

Getting the app to work is step one ("make it work"). Step two is making it right — refactoring so the next engineer can understand and evolve it. Step three is making it fast only where actually needed. Code that only ever reaches step one accumulates coupling (ORM calls scattered through route handlers, business logic embedded in components) until the codebase can no longer survive a technology change. The simplest version that fully works *and* is easy to change is the target.

## Don't gold-plate
Solve the stated problem, not imagined future scale. The simplest version that fully works is the target.

## Names reveal intent
A name should tell you why it exists, what it does, and how it is used. If a name requires a comment to explain what it does, the name fails. Prefer `elapsedTimeInDays` over `d`, `getFlaggedItems()` over `getData()`. Avoid noise words (`Data`, `Info`, `Manager`, `Processor`) and type encodings. Use one word per concept across the codebase — pick `fetch` or `get` or `retrieve`, not all three for equivalent operations in different modules. Module and function names are verbs or verb phrases; types and interfaces are nouns or noun phrases. Names at the right level of abstraction: problem-domain names where there is no technical term, solution-domain names (patterns, algorithms) where there is. The length of a name should correlate with the size of its scope — a loop variable in a five-line callback can be `i`, but a function reachable across modules needs a precise, full name. Names must also describe everything a function does, including side effects: a function that creates an object on first call and returns it thereafter should be named `createOrReturnX`, not merely `getX` — hiding a side effect under a simple verb is a temporal-coupling trap. Extract complex boolean expressions into intent-revealing predicate functions (`if canBeCompacted()` rather than inline multi-clause expressions) and prefer positive predicates over negative ones — `canBeCompacted()` is easier to reason about than `!shouldNotBeCompacted()`.

## Functions do one thing at one level of abstraction
A function does one thing when all its steps are one level of abstraction below its name — not a mix of high-level policy and low-level detail in the same body. If you can extract another function with a name that is not merely a restatement of the implementation, the function is doing more than one thing. Flag arguments (boolean parameters) reliably signal a function doing two things: split into two clearly-named functions. Side effects that a function's name doesn't declare are temporal coupling hazards. Keep functions small enough that the intent is immediately obvious; a handler or Server Action that requires deep reading to understand is a refactoring candidate.

## Comments compensate for failure to express in code
A comment that explains *what* code does is a naming or structural failure: rename, extract a function, introduce a well-named variable. Comments lie as code evolves — they rarely follow the code they describe. Use comments only when the *why* cannot be expressed in structure: a hidden constraint, a non-obvious invariant, a workaround for an external bug, or a warning of serious consequences. Legal comments, amplification of subtle requirements, and TODOs that name a concrete next action earn their place. Comments that restate code, record history, or explain what a well-named function already says do not.

## Leave it cleaner than you found it
Every time you touch code, leave it slightly cleaner than you found it — a better name, a shorter function, a removed dead branch, a missing test added. Code does not rot in one commit; it rots because each person who touched it left it marginally worse, deciding the cleanup was someone else's problem. The reverse is equally true: a codebase improves steadily when each change leaves the touched area in better shape.

Good code is not written all at once — it is refined through many small, test-preserving steps. Large structural changes should decompose into increments where the test suite is green before and after each step. If a refactoring cannot be broken into such increments, it is either too large (split it) or it changes behavior (flag it as a separate task). "Make it work → make it right → make it fast" is a mandatory sequence, not a suggestion.

## True vs. accidental duplication
Before unifying code, confirm the duplication is real. True duplication is one concept with one reason to change — every copy must change together, always. Accidental (false) duplication is code that merely looks alike today but serves different use cases and will diverge (two screens, two endpoints, two roles). Unifying accidental duplication couples things that change for different reasons and is painful to unwind — flag it as *deliberately keep separate*. A database row that happens to look like the view/response model is the classic false positive: keep them distinct types. When in doubt, let the duplication stand until the shared rule is proven.

## Simple Design — four rules in priority order
A design is simple when it (1) passes all tests, (2) contains no duplication, (3) expresses the intent of the programmer — through good names, small focused functions, and clear structure — and (4) minimizes the number of modules and functions. Follow them in that order: testability first, then eliminate duplication, then maximize expressiveness, and finally minimize count. These rules work together: writing tests pushes toward smaller, more focused units; removing duplication often reveals the right abstraction; expressiveness and minimization trade off at the margin — more modules that are clearer beat fewer that obscure intent. When you can't tell whether you're done refactoring, ask: does it pass all tests? Is there still duplication? Could a reader understand the intent without a guided tour? Are there functions or modules that do no real work?

## Dependency Rule — high-level policy must not depend on low-level detail
Source-code dependencies point inward toward the domain. The framework, the database/ORM, and any external SDK are details that should depend on your domain logic, not define it — so they stay swappable and the logic stays testable in isolation without the web server or database running. Don't leak raw DB/ORM rows or API DTOs into Client Components or through API responses; map to types you own at the boundary so storage and transport can change without cascading changes. Organize the top level so it announces the domain and its use cases — what the app *does* — not which framework built it.

## Don't marry the framework — frameworks and SDKs are details
A framework is a detail you use, not one you marry. Keep Next.js/React-specific types, Prisma/Drizzle-generated types, and third-party SDK annotations out of your domain logic. Wrap them behind a boundary (interface/port) you own and confine them to an outer layer — so you can adopt, upgrade, or replace the framework without rewriting the core.

## Lean on the toolchain to hold boundaries
Module/package seams, ESLint import rules (`no-restricted-imports` / `import/no-restricted-paths`), TypeScript project references, and `server-only` / `client-only` markers can make a forbidden dependency fail the build rather than slipping through review. Prefer that over trusting convention. Flag barrel files (`index.ts` re-export hubs) and overly-broad public exports that defeat this by making everything reachable from everywhere.

Note: the choice of architectural style — layered, feature-sliced, ports and adapters, component-based — becomes effectively meaningless if every module re-exports all its internals. When all types are globally reachable, all four styles collapse into the same flat topology regardless of folder structure. Export visibility is what gives an architectural choice its meaning; without it, the structure is labeling, not enforcement. Minimize exports to the surface the module genuinely intends to expose.

## Composition root — wire once, inject inward
Wire dependencies in one composition root (a single wiring module or per-request factory) rather than constructing them inline across route handlers, Server Actions, and components. Business logic should not `new` up a Prisma/Drizzle client or an SDK directly. This keeps the framework and SDKs as swappable outer details, gives tests one seam to substitute fakes, and stops framework/vendor types leaking inward. Think of the composition root as a *plugin*: you can have multiple — one for dev, one for test, one for prod, one per environment or tenant. The core system is never aware of which plugin is active; only the wiring module changes.

## Object peer stereotypes — know which collaborators must be injected
A module or class's collaborators fall into three categories, each with a different injection strategy:

- **Dependencies** — services the module *requires* to function at all (a database client, an HTTP client). There is no safe default. Pass them through the constructor or factory parameter; a module that cannot be created without its dependencies makes the requirement impossible to miss.
- **Notifications** — fire-and-forget observers the module informs of events (an event bus, an audit logger, an analytics callback). A missing observer is acceptable — initialize to a no-op or null object so the module can operate without one, and let callers register after construction.
- **Adjustments** — policy objects that tune the module's behavior (a retry strategy, a formatter, a feature-flag resolver, a timeout value). Safe defaults exist. Initialize to the canonical default and let callers override.

Bloated constructors are a frequent consequence of treating Notifications and Adjustments as Dependencies. When a constructor or factory grows beyond ~3–4 parameters, check each argument: if removing it would leave the module in a valid (if default) state, it is not a true Dependency — give it a default. If two or more arguments are always used together and share a lifetime, they may represent an implicit concept that deserves its own named type.

## Support logging is a feature; diagnostic logging is scaffolding
Two activities share the word "logging" but have entirely different stakeholders and design rules:

- **Support / operational logs** (error, warning, info-level events visible to ops or support staff) are part of the product's external interface. They should be test-driven from the requirements of whoever depends on them — operations, support engineers, automated monitors. Model them as a named notification object (a `Reporter` interface, a `Monitor` service) rather than scattering direct `logger.error(...)` calls through domain code. This keeps the log contract explicit, keeps domain code readable, and makes the format stable enough for scripts and dashboards to rely on.
- **Diagnostic logs** (debug, trace) are programmer scaffolding — not intended for production and not part of any contract. They do not need to be test-driven and can be written inline.

If a domain function or class must accept a logger in its constructor because support logging is scattered throughout it, that is a design smell: the function either has too many responsibilities or the support-log call belongs in a caller, not inside the domain unit.

## Minimize dependencies
Each dependency is a liability — a supply-chain risk, a bundle-size cost, and a maintenance burden. Prefer the platform and framework's built-ins.

## Resilience — assume the network and every dependency can fail or stall
Put an explicit timeout on every out-of-process call. Prefer failing fast and degrading a feature (fail a widget, not the whole page) over hanging the whole response — a slow dependency is more dangerous than a down one, because blocked requests pile up and exhaust the pool. Bound retries with backoff. Make retried or replayed effects idempotent. Read external responses tolerantly: extract only the fields you use, ignore unknown/extra ones.

When building integration tests for external services, test your application against the full range of pathological behavior — not only happy and error paths, but also: refused connections, accepted connections that are then dropped, connections that accept but never reply, responses that arrive extremely slowly, responses with unexpectedly large payloads, and responses containing garbage or malformed data. A test harness that can simulate these failure modes gives you confidence the app handles production chaos before it appears in production. Apply the **Circuit Breaker** pattern to trip and fast-fail callers when a dependency is persistently unhealthy, and the **Bulkhead** pattern to isolate failure in one integration from spreading to the rest of the app — so a third-party API going down degrades one widget, not the entire page.

## Concurrency is a separate concern
Server-side concurrency (parallel requests hitting shared state, background jobs racing with request handlers, webhook replays) has its own failure modes that are fundamentally different from single-threaded request handling. Keep concurrency orchestration separate from domain logic: a service function should not need to know whether it is called from a webhook handler, a cron job, or a route handler. Limit shared mutable state — prefer per-request scoping, immutable data, and idempotent writes over in-process counters or locks. When shared state is unavoidable (a rate-limit counter, a job-claim flag), define its ownership boundary explicitly and keep it narrow. On multi-instance hosts, in-process state is multiplied by the number of instances and cannot be trusted for coordination — use an external store (DB, cache) as the single source of truth. Concurrency bugs are non-repeatable and surface under load; the primary defense is to write domain logic in plain, framework-free functions testable without a running server, and to test concurrency behavior (replay idempotency, race conditions, graceful degradation under parallel load) explicitly and separately. Synchronize as little as possible — when in-process locking is used, keep the critical section as narrow as the actual shared-state access; wide locks serialize callers that do not need to be serialized. Prefer modules that encapsulate their own concurrency safety (server-based locking — e.g., a rate-limit counter that uses atomic operations internally) over patterns that require every caller to coordinate externally (client-based locking) — when a module is responsible for protecting its own state, callers cannot forget to do it.

## Tell, don't ask — Law of Demeter
A module should only call methods on: itself, objects it creates, objects passed as arguments, and objects it holds directly. Avoid chains that navigate through multiple layers — `a.getB().getC().doSomething()` exposes internal structure, couples the caller to every intermediate type, and means a change to any link in the chain requires updating the caller. When you find yourself navigating through a dependency's internals to reach what you need, tell the nearest object to perform the operation and let it delegate internally. If it doesn't expose that operation, add a well-named method to it rather than reaching inside. This is especially important at service/data-layer boundaries where components chain through ORM-generated relations instead of calling a service method.

## Return empty objects, not null
When a query finds nothing, returning null/undefined forces every caller to guard before using the result. Instead, return a special-case value that behaves correctly in the "nothing here" state: an empty array over null, a zero-value object, or a lightweight null-object default. Callers use the return value directly without null-checks, and the "not found" handling lives in one place — the returning function — rather than scattered across all callers. Reserve null/undefined for cases where the caller genuinely needs to distinguish absence from presence and acts differently on each; for simple "nothing found" results, prefer the empty or default form. Relatedly, avoid returning sentinel error codes (−1, 0, a magic string like `"error: ..."`) to signal failure. Callers cannot reliably distinguish a sentinel from a legitimate result, must remember to check it, and often don't. Use thrown errors or typed discriminated unions for failures and reserve return values for meaningful data.

## Feature envy — functions belong where the data lives
A function or method that spends most of its time accessing another module's or object's data and calling its methods probably belongs in that module. When a function body is dominated by `user.subscription.plan.features`-style navigation or repeated `other.getX()`, `other.getY()` to feed a local calculation, ask whether the operation should live closer to the data — and move it. Common exceptions: Strategy and Visitor patterns that deliberately cross boundaries when the design is intentional.

## Temporal coupling — expose execution order in the signature
When functions must be called in a fixed order, make that constraint impossible to violate rather than documenting it. The canonical fix: have step N return a typed value that step N+1 requires as a parameter, so TypeScript prevents out-of-order calls. A comment that says "call initializeSession() before processing" is a hidden temporal coupling; a parameter type that proves the step ran is an explicit one. Flag middleware chains and multi-phase setup where ordering is enforced only by convention rather than types.

## Encapsulate boundary conditions
Boundary calculations are easy to get wrong and easy to miss when scattered. When a boundary expression appears (e.g., `n + 1`, `last - 1`, `array.length - 1`), capture it in a single named constant or variable rather than repeating the arithmetic at every use site. One named variable is easier to review, reason about, and change than the same expression spread across a function body.

## Use explanatory variables
Break complex calculations into intermediate results with meaningful names. Even when an intermediate value is used only once, assigning it to a well-named constant documents what the sub-expression means — without a comment. `const nextLevel = currentLevel + 1` is clearer than scattering `currentLevel + 1` through the surrounding code. This is the simplest, cheapest form of self-documenting code.

## Implement boundaries at the inflection point
Architectural boundaries cost money to implement and cost money to leave out. Don't add them speculatively up front (YAGNI applies), but watch for the friction that signals one is needed: two concerns changing at different rates, inability to test one thing without standing up another, or a "small" feature requiring coordinated changes across many unrelated routes and modules. When that friction appears, weigh the ongoing cost of ignoring the boundary against the one-time cost of drawing it — and implement it when the former exceeds the latter. Revisit this judgment frequently; it is not a one-time decision.

## Keep configurable data at high levels
Constants, defaults, and configuration values that are known at a high level of abstraction should be declared there and passed downward as arguments — not buried in low-level functions or hardcoded deep in the implementation. When a constant lives close to where it is used but far from where it conceptually belongs, readers must search through implementation layers to understand what values the system runs on. Declare defaults and tunable values at the entry point or configuration layer, expose them as explicit arguments or environment variables, and let lower-level modules receive them rather than re-derive them. Logical dependencies — assumptions a module makes about another module without asking it — should be made physical: if a caller assumes a downstream can handle a batch size of 100, the downstream should expose `maxBatchSize()` so the assumption is encoded in a real API rather than an undocumented constraint.

Never bake environment-specific values — API hostnames, service URLs, feature switches, secrets — into the application bundle or built artifact. Any value that differs between environments (dev / staging / prod) must be injected at build or run time (via environment variables, a `.env` file loaded server-side, or a configuration service) so the same artifact can be promoted through environments unchanged. A build with production endpoints hardcoded cannot be safely exercised in staging; a build that receives them at run time can be verified anywhere and released with confidence. Treat configuration as a first-class artifact: version it, test it (smoke-test that referenced services are reachable after deploy), and never check secrets into version control.

## If it hurts, do it more frequently — bring the pain forward
When an activity is painful, the instinct is to do it less often. The correct response is the opposite: do it more often, and sooner. Integration done on every commit cannot accumulate the explosive merge debt that integration done monthly produces. Deployment rehearsed in every environment loses its ceremony. Testing deferred to the end discovers defects when they are most expensive to fix; testing continuously from day one discovers them when they are cheapest. When you find yourself dreading an activity — merging, deploying, writing tests, updating documentation — treat that dread as a signal that the activity contains unresolved complexity worth surfacing now rather than later.

## Build quality in — testing is not a phase
Everyone on a delivery team is responsible for quality all the time, not just testers, and not just at the end of a cycle. A test written alongside the code it verifies is cheapest and most accurate. A test written weeks later is often a transcription of the implementation rather than a specification of the intent — it proves the code ran, not that it was correct. Build automated tests at every level (unit, integration, acceptance) from day one. A feature is only done when it passes its acceptance criteria in a production-like environment, not when it compiles locally or when unit tests are green in isolation. Each handoff of a defect between people multiplies the cost to fix it; the cheapest fix is the one that never leaves the developer's machine.

## Cycle time is the global metric — optimize end-to-end, not locally
The most important delivery metric is **cycle time**: the elapsed time between deciding a change is needed and having that change in users' hands. Secondary metrics — test coverage percentage, defect count, build duration, velocity — are diagnostics for investigating a problem in cycle time, not goals in themselves. Optimizing a local metric that is not the bottleneck produces no improvement in cycle time and can even make it worse. The lean test: "How long would it take to get a single-line change from commit to production, reliably and repeatably?" If that answer is measured in weeks, the bottleneck is somewhere in the process — find it, exploit it, then find the next one.

When defects accumulate in a backlog, make them visible: display count, trend, and priority alongside features rather than hiding them in a separate system. A growing silent backlog is a sign that cycle time for bugs is too long, and that quality issues are not being resolved at the rate they are discovered. Bugs that are never fixed tend to be bugs nobody knows about.

## Surface trade-offs explicitly
Don't bury decisions in code. A constraint, a risk, or a rejected alternative worth knowing belongs in a plan, a comment, or a handoff note — not silent in the implementation.

## Ask when uncertain
A question is cheaper than a wrong implementation. If a decision is genuinely ambiguous, surface it rather than guessing.

## Cite current documentation
When a decision rests on current framework or host behavior, cite the official Next.js documentation or the confirmed host's docs. Training data can be behind; official sources take precedence over community convention.
