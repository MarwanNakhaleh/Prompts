# MCP Engineering Principles

These principles apply to every prompt in `mcp/` — build-server, feature-dev, and any future ones. They are the background framework for every architecture, implementation, and audit decision an MCP server in this category goes through.

When making decisions that depend on current behavior — the MCP spec's tool/resource/prompt primitives, structured-output and content types, transport and auth obligations, the official SDK surface, or any upstream API a server wraps — consult `mcp/resources.md` first. It lists the authoritative, regularly-updated source for each slice so you ground decisions in live documentation rather than training-data memory, which moves fast here and is easily stale.

## A tool's blast radius is whatever it can do
An MCP server is not a library you call; it is production access handed to an autonomous model you do not control, which will invoke a tool whenever its description says to. The blast radius of a tool is therefore whatever that tool can do — and a tool that can spend money, mutate production state, or take an irreversible outward-facing action carries the blast radius of that action every time the model decides to call it. This single fact reorders the architecture: capability gating, safe-by-default state, the human-approval gate, write rate limits, and the append-only audit log are not features bolted on after the tools work — they are load-bearing structure from the first commit, the same way memory safety is structural rather than a feature in a systems language.

Concretely, this means the policy layer is a single cross-cutting seam every write passes through, not logic copied into each adapter where one adapter can forget it. A tool is tagged with a risk tier — read-only, reversible write, or irreversible/spend — and that tier is checked against the active capability flag before the tool runs, so a tool whose tier exceeds the active flag is simply uncallable. This mirrors the operating doctrine of `marketing/connect-ad-platforms.md` — except applied to a server you *build* rather than a platform you connect to, which raises the stakes: you own the gate, so a gap in it is your defect, not the host's.

## Tool descriptions are the model's interface
The model knows nothing about your server except what the tool name, description, and argument schema tell it. Those three things *are* the interface to the model, and they are the highest-leverage reliability lever you have — a bad or ambiguous description causes the model to call the wrong tool, pass the wrong arguments, or skip a tool it should have used, the same way a misleading type signature causes a human to write wrong code. A tool named `update` with a vague description is the MCP equivalent of a function named `getData()`: it tells the caller nothing about why it exists, what it does, or when to reach for it.

Treat descriptions as first-class engineering artifacts. Keep them in versioned prompt files, not buried inline as an afterthought next to the handler, so they can be reviewed, diffed, and tuned independently of the adapter code. Tune them per runtime model — a description that elicits correct tool calls from one model may mislead the next — and test them with an eval harness that measures tool-call reliability, not just unit tests that prove the handler runs. The argument schema is part of this contract: a strict, well-named schema with clear field descriptions guides the model toward valid calls and lets the boundary reject invalid ones with a structured error the model can recover from.

## Model-agnostic by design
MCP is model-agnostic by design, and the server must honor that: it must not assume which model or host calls it. The line to keep clean is the boundary between adapter code — stable, owned by you, wrapping upstreams — and the agent harness plus tool-description tuning, which is per-model and swappable. Keep the runtime model and client harness in config, and keep the tool descriptions, system prompt, and few-shot examples in versioned prompt files separate from adapter code. A model swap is then a config-and-prompt change that touches no adapter, never a rewrite.

Assume prompts tuned against one model need a re-tuning pass for the next; transfer is rarely clean. This is why the eval harness matters whenever the model is swappable — it is the mechanism that tells you a prompt that worked on model A still elicits correct tool calls on model B. Designing for the swap before it's needed is gold-plating if a single host is the only target; confirm the requirement before building the boundary, but keep the seam clean enough that introducing it later is a config-and-prompt refactor rather than an adapter rewrite.

Keep two model-switch axes distinct, because they live in different places. The **runtime LLM that drives the server** is the config boundary above — swapped at the composition root, never in an adapter. A **media-generation model a tool calls** is something else entirely: when a server exposes creative-generation tools (text-to-speech, music, image, video) by calling an external media-generation API from inside a tool, the choice of generation model is a tool/provider config plus a per-call parameter, not the runtime-LLM knob. Model each generation capability as its own provider **port** — `SpeechProvider`, `MusicProvider`, `VideoProvider` — with vendor adapters swappable by config, applying the same ports-and-adapters discipline as the upstream data adapters: the verb layer depends on the port, the vendor SDK stays behind the adapter, and the generated media maps to a response shape you own. Conflating the two axes — routing the media model through the runtime-LLM config, or hardwiring a vendor SDK into a tool handler — collapses a boundary that wants to stay clean.

## Compose official upstream servers before reimplementing; vet third-party
Where an official upstream MCP server exists for a capability, proxy or compose it rather than rebuilding its API behind your own adapter — reimplementing what an official server already maintains is duplicated effort that you then own forever and that drifts from the upstream as it evolves. Reach for the upstream's direct API only for capabilities its official server lacks. This is the same instinct as preferring a platform built-in over a hand-rolled implementation: the maintained thing is usually the simpler thing.

A third-party (non-official) MCP server is a different risk class entirely. It sees both your data *and* your access tokens, so it is a supply-chain dependency with credential access — vet the maintainer before composing it, and never use one that risks an account ban on the upstream it touches. When no official server exists and the only option is a third-party one you cannot vet, calling the upstream API directly behind an adapter you own is the safer path even though it is more code.

## Simplicity is the deliverable
If two solutions work, ship the one that's easier to read and delete. Optimize for readability and the next engineer who maintains this. Unnecessary abstraction, premature generalization, speculative flexibility, and dependency bloat are bugs.

Getting the server to respond is step one ("make it work"). Step two is making it right — refactoring so the next engineer can understand and evolve it. Step three is making it fast only where actually needed. Code that only ever reaches step one accumulates coupling (SDK calls scattered through tool handlers, upstream API DTOs leaking into tool results, policy checks copied per adapter) until the server can no longer survive a model swap or an upstream API change. The simplest version that fully works *and* is easy to change is the target.

## Don't gold-plate
Solve the stated problem, not imagined future scale. The simplest version that fully works is the target. A v1 read-only server for one host does not need multi-tenant isolation, every capability tier enabled, or a model-swap boundary that no requirement asks for — leave a clearly-marked extension hook instead of building the thing.

## Names reveal intent
A name should tell you why it exists, what it does, and how it is used. If a name requires a comment to explain what it does, the name fails. This is doubly true for tool names, which the model reads as its only interface — prefer `list_campaigns` over `get`, `create_draft_campaign` over `make`. Avoid noise words (`Data`, `Info`, `Manager`, `Handler`) and type encodings. Use one word per concept across the server — pick `fetch` or `get` or `retrieve`, not all three for equivalent operations in different adapters. Functions and tools are verbs or verb phrases; types and ports are nouns or noun phrases. Names at the right level of abstraction: problem-domain names where there is no technical term, solution-domain names (patterns, algorithms) where there is. The length of a name should correlate with the size of its scope. Names must also describe everything a function does, including side effects: a tool that creates an object and a separate one that publishes it must be named so the difference is unmistakable — hiding the publish under a `create`-shaped name is both a temporal-coupling trap and a safety hazard. Extract complex boolean expressions into intent-revealing predicate functions (`if writeIsPermitted()` rather than inline multi-clause expressions) and prefer positive predicates over negative ones.

## Ubiquitous language — align code vocabulary with the domain
The names in the code should match the vocabulary used by the domain experts and the upstream platforms the server wraps — not merely names that are technically accurate. When the ad platform calls it a "campaign" but your code calls it a "job," or the API says "ad set" but your verb says "group," there is an invisible translation layer living in every engineer's head that never makes it into code or tests. This translation accumulates silently and compounds into a server that models an engineer's interpretation of the upstream rather than the upstream itself.

The practice: when wrapping an upstream, learn the specific words its API and its users use, and use those exact words in tool names, verb names, argument schemas, and response types — not synonyms, not abbreviations, not generic terms where the platform has a specific one. The unified verb layer is where you may *deliberately* introduce a platform-agnostic vocabulary across several upstreams; that is a designed translation, named once and documented, not an accidental one living in each engineer's head. When the model's tool description and the upstream's docs use the same word for the same thing, the language is working.

## Functions do one thing at one level of abstraction
A function does one thing when all its steps are one level of abstraction below its name — not a mix of high-level policy and low-level detail in the same body. If you can extract another function with a name that is not merely a restatement of the implementation, the function is doing more than one thing. Flag arguments (boolean parameters) reliably signal a function doing two things: split into two clearly-named functions — a `create(publish=True)` tool is two tools wearing one name and one of them is a safety-gated action. Side effects a function's name doesn't declare are temporal-coupling hazards. Keep a tool handler small enough that its intent is immediately obvious; a handler that validates, gates, calls an upstream, maps the response, and writes the audit log inline is doing five things and should orchestrate five named units.

## Comments compensate for failure to express in code
A comment that explains *what* code does is a naming or structural failure: rename, extract a function, introduce a well-named variable. Comments lie as code evolves — they rarely follow the code they describe. Use comments only when the *why* cannot be expressed in structure: a hidden constraint (an upstream's edit-frequency limit), a non-obvious invariant, a workaround for an upstream API bug, or a warning of serious consequences (why a tool is gated to the highest tier). Legal comments, amplification of subtle requirements, and TODOs that name a concrete next action earn their place. Comments that restate code or explain what a well-named tool already says do not.

## Leave it cleaner than you found it
Every time you touch code, leave it slightly cleaner than you found it — a better tool description, a shorter handler, a removed dead branch, a missing contract test added. Code does not rot in one commit; it rots because each person who touched it left it marginally worse, deciding the cleanup was someone else's problem. The reverse is equally true: a server improves steadily when each change leaves the touched area in better shape.

Good code is refined through many small, test-preserving steps. Large structural changes should decompose into increments where the test suite and the eval harness are green before and after each step. If a refactoring cannot be broken into such increments, it is either too large (split it) or it changes behavior (flag it as a separate task). "Make it work → make it right → make it fast" is a mandatory sequence, not a suggestion.

## True vs. accidental duplication
Before unifying code, confirm the duplication is real. True duplication is one concept with one reason to change — every copy must change together, always (the policy-gate check that must be identical across every write path is true duplication, and belongs in one seam). Accidental (false) duplication is code that merely looks alike today but serves different use cases and will diverge — two adapters whose response-mapping happens to look similar today but tracks two upstreams that evolve independently. Unifying accidental duplication couples things that change for different reasons and is painful to unwind — flag it as *deliberately keep separate*. An upstream API DTO that happens to look like the structured tool-output shape is the classic false positive: keep them distinct types so the upstream can change its wire format without changing your tool contract.

## Simple Design — four rules in priority order
A design is simple when it (1) passes all tests, (2) contains no duplication, (3) expresses the intent of the programmer — through good names, small focused functions, and clear structure — and (4) minimizes the number of modules and functions. Follow them in that order: testability first, then eliminate duplication, then maximize expressiveness, and finally minimize count. These rules work together: writing tests pushes toward smaller, more focused units; removing duplication often reveals the right abstraction; expressiveness and minimization trade off at the margin — more modules that are clearer beat fewer that obscure intent. When you can't tell whether you're done refactoring, ask: does it pass all tests and evals? Is there still duplication? Could a reader understand the intent without a guided tour? Are there functions or modules that do no real work?

## Cohesion — keep things that belong together, together
Cohesion is the positive counterpart to coupling: while loose coupling reduces unnecessary dependencies *between* modules, high cohesion keeps strongly related elements *within* the same module. A module is highly cohesive when all its exports work together toward a single clearly defined purpose, and removing any one would leave the purpose incomplete.

The strongest form is **functional cohesion** — the module does exactly one well-defined thing. Weaker forms are warning signs: **communicational cohesion** (an adapter that fetches, validates, gates, and audits all in one); **temporal cohesion** (functions grouped because they happen at the same time — a server-bootstrap function that loads config, opens the token store, registers tools, and pings an upstream all in one body); **coincidental cohesion** (the `utils` / `helpers` module that accumulates unrelated functions over time). The naming test is reliable: if a module's purpose cannot be stated in one sentence without the word "and," its cohesion is less than functional — split along the lines where the "and" appears. A module you struggle to name is almost always a module whose cohesion has not been found yet.

## Dependency Rule — high-level policy must not depend on low-level detail
Source-code dependencies point inward toward the domain — the unified verbs and the policy layer. The MCP SDK, the transport (stdio/HTTP), the upstream API clients, and any vendor SDK are details that should depend on your domain logic, not define it — so they stay swappable and the logic stays testable in isolation without a running transport or a live upstream. Don't leak raw upstream API DTOs or SDK types into verb signatures, policy decisions, or tool results; map to types you own at the boundary so the wire format and the SDK can change without cascading inward. The verb layer and the policy layer must be exercisable by a plain unit test with fake adapters — no server process, no network. If they aren't, a detail has leaked inward.

## Stable Dependencies Principle — depend in the direction of stability
Dependencies should flow toward stability: volatile modules (a specific adapter, a tool handler, code under active development) may depend on stable modules, but a stable, widely-imported module must never depend on a volatile one. Stability means *number of dependents*, not *frequency of change* — a module is stable when many things import it, because changing it forces changes in every consumer. The corollary: the most stable modules should be the most abstract — the port interfaces, the policy contracts, the response types — with minimal or no concrete implementation. The port interface an adapter implements is depended on by the verb layer, the composition root, and the tests; it must stay abstract. A widely-imported *concrete* module (an SDK client imported directly by many handlers) is a design hazard — that is the signal to extract a port interface in front of it so consumers evolve independently of the concrete implementation.

## Don't marry the SDK or framework — they are details
The MCP SDK is a detail you use, not one you marry. Keep SDK-specific types (the server object, request/response wrappers, content-type helpers), vendor API client types, and transport specifics out of your verb layer and policy layer. Wrap them behind a boundary — a port interface — you own, and confine them to an outer layer, so you can adopt, upgrade, or replace the SDK, swap stdio for streamable HTTP, or change an upstream client without rewriting the core. The MCP SDK is a server toolkit, not a web framework; treating it like one (routing business logic through SDK callbacks, shaping the domain around its primitives) marries you to it.

## Favor composition over inheritance
When one module needs the behavior of another, prefer holding it as a composed dependency over extending or inheriting from it. Inheritance is a compile-time bond: a subclass is exposed to its parent's implementation, and changes to the parent can silently break the subclass — *inheritance breaks encapsulation*. Composition keeps each unit behind its own interface and lets the relationship change across configurations. Implement an interface (a port) when committing to a behavioral contract; hold concrete behavior as a composed collaborator injected at the wiring layer. A base `Adapter` class that every upstream adapter extends for shared retry logic is the common trap — that shared behavior is a composed resilience helper the adapters *hold*, not a parent they *are*.

## Liskov Substitution Principle — subtypes must honor the full contract
A type that implements a port interface must be fully substitutable for any other implementor without callers needing to know which concrete adapter they have. This is a behavioral claim, not just a type-shape claim a type-checker can verify. Substitutability requires: (1) do not strengthen preconditions — if the port says a verb accepts any valid filter, an adapter that only handles a subset is a violation; (2) do not weaken postconditions — if the port implies a verb returns a populated result, an adapter that returns null in some cases violates the contract; (3) do not introduce new failure modes the port doesn't declare — an adapter that throws a raw SDK error where the port declares a domain error breaks every caller's error handling; (4) preserve invariants the port establishes — including that every write goes through the policy gate.

Common violations: a fake adapter used in tests that throws errors the real adapter never would; a port implementation where several verbs are empty stubs or raise "not implemented"; an adapter that returns a different structured-output shape than the port's contract promises. Type-checkers (mypy/pyright, `tsc`) check shapes, not behavioral contracts — violations pass type-checking and surface only at runtime against the real upstream. The diagnostic: if implementing a port requires stubbing verbs with "not implemented" or returning null where the contract implies a real value, the port is probably too large or this adapter shouldn't implement it.

## Interface Segregation — keep ports narrow to one client's needs
A port interface should contain only the verbs its specific clients need. When a port accumulates verbs serving different callers, each adapter is forced to satisfy verbs it doesn't support — often with empty bodies or "not implemented" stubs that silently violate the contract callers depend on. A read-only upstream forced to implement a fat `Adapter` port with write verbs is the canonical case: it stubs the writes, and a caller trusting the port can invoke a write that is secretly a no-op.

The fix is to decompose the fat port into focused ones, each sized to the needs of one caller — a `ReadPort` for query verbs and a `WritePort` for mutation verbs, so a read-only upstream implements only the reader and the capability flag has a natural shape to gate against. An adapter may implement multiple focused ports. The diagnostic: count how many of a port's verbs any single adapter implements meaningfully. If most adapters use only a subset and stub the rest, the port is too broad. This applies to a server's tool surface too: exposing twenty tools where the host only ever calls three is the same anti-pattern applied to the model's interface.

## Lean on the toolchain and type-checker to hold boundaries
Module/package seams, import-restriction lint rules, type-checker strictness (mypy/pyright in Python, `tsc` in TypeScript), and explicit package boundaries can make a forbidden dependency fail the build rather than slipping through review — an SDK import inside the verb layer, an upstream DTO in a tool result, a policy bypass in an adapter. Prefer that over trusting convention. Flag barrel/re-export hubs and overly-broad public exports that defeat this by making everything reachable from everywhere.

The choice of architectural style — ports and adapters here — becomes meaningless if every module re-exports all its internals. When the SDK client and the raw upstream DTOs are reachable from anywhere, the adapter boundary collapses into a flat topology regardless of folder structure. Export visibility is what gives the boundary its meaning; minimize exports to the surface each module genuinely intends to expose, and keep the SDK and vendor clients reachable only from the adapter and composition root.

## Information hiding — modules hide design decisions that might change
The right criterion for a module's boundary is not "what does this module do?" but "what design decision does this module hide?" Every module should conceal one decision that might be revised — so when that decision changes, only the module that hides it changes. The secret might be: which upstream API provides a capability, how tokens are structured and stored, whether you compose an official MCP server or call the API directly, how the audit log is persisted, which transport carries the protocol, how rate-limit counters are kept. The module's public interface is designed so all callers can be served *without knowing the secret*.

This is the principle that makes "don't marry the SDK" and the Dependency Rule coherent. A vendor SDK's concreteness is a decision that might change (direct API → official MCP server, REST → gRPC); hiding it behind a port means the verb layer is insulated from the change. Conversely: when a change to an adapter forces a change in the verb layer, the adapter leaked its secret — a vendor DTO reached the verb signature, so the verb now knows which upstream it talks to. The fix is not to make the verb layer more tolerant; it is to redesign the adapter's interface so the leaking type is no longer part of the contract. When designing a port, ask: "What would I need to change if I replaced this upstream completely?" Everything in the answer is a candidate to hide behind the port rather than expose through it.

## Composition root — wire once, inject inward
Wire dependencies in one composition root (a single server-bootstrap module) rather than constructing them inline across tool handlers. A handler should not `new` up an SDK client, open the token store, or instantiate the audit logger directly. This keeps the SDK and vendor clients as swappable outer details, gives tests one seam to substitute fake adapters and an in-memory audit log, and stops vendor types leaking inward. Think of the composition root as a *plugin*: one wiring for dev, one for test (fakes, recorded fixtures, in-memory stores), one for prod. The core verbs and policy are never aware of which plugin is active; only the wiring module changes — which is also how the model-swap boundary works, with the runtime model and harness selected in config at this same root.

## Object peer stereotypes — know which collaborators must be injected
A module's collaborators fall into three categories, each with a different injection strategy:

- **Dependencies** — services the module *requires* to function at all (an upstream adapter, the token store, the audit-log writer). There is no safe default. Pass them through the constructor or factory parameter; a verb layer that cannot be created without its adapters and its policy gate makes the requirement impossible to miss — and makes it impossible to accidentally build a write path with no audit log.
- **Notifications** — fire-and-forget observers the module informs of events (a metrics sink, an analytics callback). A missing observer is acceptable — initialize to a no-op so the module operates without one. Note that the audit log is *not* a notification despite resembling one: it is a required dependency of every write path, because a mutation that fails to record is a safety defect, not a missed notification.
- **Adjustments** — policy objects that tune behavior (a retry strategy, a rate-limit configuration, a timeout value, the active capability flag). Safe defaults exist — and for capability flags the safe default is the *least*-privileged tier (`read_only`). Initialize to the canonical safe default and let the composition root override.

Bloated constructors come from treating Notifications and Adjustments as Dependencies. When a constructor grows beyond ~3–4 parameters, check each: if removing it leaves the module in a valid (if default) state, it is not a true Dependency — give it a default. Fields in the same module should change at roughly the same rate; a field updated per-session sitting beside one updated per-tool-call signals mixed responsibilities and a candidate for extraction.

## Composite simpler than sum of parts
When several modules are composed into one — the verb layer composing the policy gate, an adapter, and the audit writer — the composite's API must present a simpler, higher-level abstraction than any component individually. A composite that exposes the union of all component interfaces has not achieved abstraction; it has moved complexity to a different address. The unified verb `create_campaign` should hide that it consults a capability flag, calls an approval gate, throttles a writer, invokes a vendor SDK, and appends an audit record — a caller uses the verb without knowing how many parts it contains. If the verb's surface is larger or more complicated than any single part, the boundary is drawn wrong.

## Support logging is a feature; the audit log is a contract; diagnostic logging is scaffolding
Three activities that look like "logging" but have entirely different stakeholders and design rules:

- **Support / operational logs** (error, warning, info events visible to ops) are part of the product's external interface. Test-drive them from the requirements of whoever depends on them — operators, automated monitors. Model them as a named notification object (a `Reporter` or `Monitor`) rather than scattering direct `logger.error(...)` calls through verb and adapter code, so the contract stays explicit and the format stays stable enough for dashboards.
- **The audit log** is a separate, stronger thing — an append-only contract recording every mutation, covered in its own section below. It is required infrastructure, not operational convenience.
- **Diagnostic logs** (debug, trace) are programmer scaffolding — not production, not a contract. They need not be test-driven and can be written inline.

If a verb must accept a logger because support logging is scattered through it, that is a design smell: it either has too many responsibilities or the support-log call belongs in a caller. Across all three, the iron rule from the secrets section holds — no token, client secret, or PII ever enters any log line.

## The audit log is an append-only contract
Every mutation an MCP server performs is recorded in an append-only audit log: who initiated it, what was done, when, and the before→after state. This is not diagnostic scaffolding you can omit under deadline; it is the record that makes an autonomous-model-driven server accountable, and it is load-bearing safety architecture. Treat it like support logging — a designed notification surface with a stable, queryable format that scripts and humans depend on — not like a debug print.

Three properties are non-negotiable. It is **append-only**: entries are never edited or deleted, so the history of what the model did cannot be rewritten. It is **durable**: it survives a process restart, written to durable local storage (or an external store on multi-instance remote deploys, where in-process state cannot be trusted). And it **never contains secrets or PII**: tokens, client secrets, and personal data are redacted at the boundary, because the audit log is itself a new leak vector — a place engineers reasonably assume is safe to dump everything into. A write path that completes without an audit entry is a defect of the same severity as a write that bypasses the approval gate. The audit writer is therefore a required dependency of the verb layer, injected at the composition root, never an optional notification a handler may forget.

## Observability — three signals
A server driven by an autonomous model you don't control is a black box in production without explicit instrumentation: you cannot answer "what tool did the model call, why did it fail, and how slow was the upstream?" from a stack trace after the fact. Wire observability from the first slice — retrofitting it into an untouched server is far more expensive than building with it. Three distinct signals address different questions and must not be conflated, and all three obey the secrets rule: no token, client secret, or PII ever enters a log line, a metric label, or a span.

- **Structured logs** answer *what happened and when*. Emit machine-parseable tool-call events around domain transitions, not code structure — `tool_invoked`, `write_gated`, `approval_denied`, `manual_step_surfaced` — secret/PII-redacted at the boundary and consistent with the audit-log rule (the audit log is the stronger, append-only contract; these operational logs are the queryable event stream around it).
- **Metrics** answer *how often and how much*. Tool-call counts, error rate per tool, **upstream latency at p50/p95/p99** (an average hides the tail, and the p99 of one upstream call compounds across every fan-out), rate-limiter rejections, and the approval-gate hit rate. Metrics tell you *when* something changed — the starting point for every production investigation.
- **Traces** answer *how did this one tool call flow through the server*. Tie a single tool call into one timeline from registration → policy layer → adapter → upstream and back, so where time was spent and where a failure occurred are visible without a local repro.

When adding a significant tool, ask: if this fails in production, what signal tells on-call something is wrong, and what lets them diagnose it without a repro? Consult the OpenTelemetry entry in `mcp/resources.md` for the vendor-neutral wiring.

## Minimize dependencies
Each dependency is a liability — a supply-chain risk, a maintenance burden, and, for an MCP server, a potential credential-access surface. Prefer the SDK's and the language's built-ins. This applies with extra force to third-party MCP servers and clients you compose: each one that touches your tokens is a dependency with credential access, weighed against the official server or the direct-API-behind-your-own-adapter alternative.

## Safe by default; read before write
Every object an MCP server creates lands in the safest possible state — PAUSED, draft, disabled — never live, never spending, never outward-facing on creation. Going live or spending is a *separate*, explicitly-gated action, never a side effect of creating or analyzing something. A `create_campaign` verb that publishes as part of creation is a design defect: it fuses a reversible action and an irreversible one under a single tool the model can call without a second gate.

Read-only is verified first and stood up first — a connection to an upstream is not trusted until a real read against the expected account succeeds, and most early use of any server should be read-only. The progression read → reversible write → irreversible/spend maps directly onto the capability tiers, and the safe default at every layer is the lower-risk one: fewer scopes, paused state, read-only flag, local stdio. When in doubt about a tier, default down and ask.

When a capability simply **cannot be automated** — an approval-gated upstream step the API won't perform headless, a credential the API can't mint, a console-only action — the tool must return a **clear, structured set of human instructions** ("do exactly X in the platform UI") rather than failing opaquely, and must **record in the audit log that a manual step was surfaced**. This is the complement to the approval gate, not a substitute: the gate stops automated spend the server *could* perform; manual-step guidance hands off cleanly when the server *can't* perform the action at all. Both keep the model from silently dead-ending — one by refusing, one by instructing.

## Never expose secrets
Tokens, client secrets, and API keys live in the credential store or the environment — never in code, chat, logs, the audit trail, or git. There is always a revocation/teardown path so a leaked or rotated credential can be killed. This is partly a consequence of "keep configurable data at high levels," but it earns its own section because an MCP server adds leak vectors a typical app doesn't have: the audit log (which engineers fill liberally), tool results returned to the model and surfaced in a host's chat transcript, and error messages echoed back through the protocol. Redact at every one of these boundaries. A token that appears in a tool result has been handed to a model and possibly displayed in a chat UI — treat that as a disclosure. Structure token storage keyed by an abstract `account_id` so multi-account today and multi-tenant later are the same shape, and so revocation is per-account and precise.

## Resilience — assume every upstream can fail or stall
Put an explicit timeout on every out-of-process call — every upstream API request, every composed MCP server call. A slow upstream is more dangerous than a down one: it hangs the tool call and, on a remote server, ties up a connection while the model waits. Prefer failing a single tool fast and degrading that capability over hanging the whole server. Bound retries with backoff. For mutations (a write, a spend, a publish), pass an explicit idempotency key so a retried write doesn't double-apply — double-spending because of a naive retry is exactly the irreversible blast radius the policy layer exists to prevent. Read upstream responses tolerantly: extract only the fields you use, tolerate unknown ones, handle unexpected enum values with a fallback.

Capability-flag and approval-gate discipline is part of resilience, enforced by failing fast and loud at the boundary: a tool whose risk tier exceeds the active capability flag must be *uncallable*, rejected at the policy seam with a clear structured error before any upstream is touched — not allowed to run and fail deep inside an adapter. The same for a write that reaches the approval gate without a confirmation the agent cannot self-satisfy: refuse it at the gate. When building integration tests, exercise the full range of pathological upstream behavior — refused connections, accepted-then-dropped connections, connections that never reply, extremely slow responses, oversized payloads, and garbage data — plus the policy failure modes: a write attempted under `read_only`, a spend without approval, a retry storm against the rate limiter. Apply the **Circuit Breaker** pattern to fast-fail callers when an upstream is persistently unhealthy and the **Bulkhead** pattern so one failing upstream degrades one capability, not the whole server. For a remote server you operate, complement these with **load shedding** — reject excess requests when approaching capacity rather than entering a metastable failure state.

## Concurrency is a separate concern
A remote MCP server handles parallel tool calls hitting shared state — rate-limit counters, idempotency keys, approval records, the audit log — and those have failure modes fundamentally different from a single-threaded stdio server processing one call at a time. Keep concurrency orchestration separate from verb and policy logic: a verb should not know whether it is called from a stdio loop or a multi-connection HTTP server. Limit shared mutable state — prefer per-call scoping, immutable values, and idempotent writes over in-process counters. On a multi-instance remote deploy, in-process state (a rate-limit counter, a seen-idempotency-key set) is multiplied by the instance count and cannot be trusted for coordination — use an external store as the single source of truth, or the rate limit you think you enforce is actually N times looser. Concurrency bugs are non-repeatable and surface under load; the primary defense is verb and policy logic written as plain functions testable without a running transport, plus explicit, separate tests for replay idempotency and concurrent-write races. Synchronize as little as possible, and prefer modules that encapsulate their own concurrency safety over patterns requiring every caller to coordinate externally.

## Tell, don't ask — Law of Demeter
A module should only call methods on: itself, objects it creates, objects passed as arguments, and objects it holds directly. Avoid chains that navigate through multiple layers — `adapter.client().session().account().name` exposes internal structure, couples the caller to every intermediate type, and means a change to any link forces a change in the caller. When you find yourself navigating through an adapter's internals or an SDK response's nested shape to reach what you need, tell the nearest object to perform the operation and let it delegate internally. If it doesn't expose that operation, add a well-named verb to the port rather than reaching inside — which also keeps the SDK's response shape from leaking past the adapter boundary.

## Return empty objects, not null
When a verb finds nothing, returning null/None forces every caller — and every tool result the model parses — to guard before using the result. Instead, return a special-case value that behaves correctly in the "nothing here" state: an empty list over null, a zero-value object, a structured-output result with an empty collection. The "not found" handling then lives in one place — the verb — rather than scattered across callers and tool handlers. Reserve null for cases where the caller genuinely needs to distinguish absence from presence and acts differently on each. Relatedly, avoid sentinel error codes (−1, a magic string) to signal failure: callers can't reliably distinguish a sentinel from a legitimate result, and a model parsing a tool result certainly can't. Use thrown domain errors or typed result unions for failures, mapped to a clear structured error at the tool boundary, and reserve return values for meaningful data.

## Fail fast — detect invalid state at the point of entry
When a value is constructed or received that violates a known invariant, surface the failure immediately and loudly — at the point where the violation occurs — not silently downstream where it causes a confusing, distant symptom. A spend amount that permits negatives, a date range where end precedes start, a verb layer wired without its audit writer, or a tool call whose risk tier exceeds the active capability flag are all invalid at the boundary; the failure should be unambiguous there, not when the value reaches an upstream ten frames later.

Three tools: (1) **Make illegal states unrepresentable** — design types whose constructors validate, so an invalid spend or a write tool with no gate cannot be built. (2) **Use the type system** — a validated-input type produced only by the boundary schema makes unvalidated input unpassable where validated input is required; a `WritePort` distinct from a `ReadPort` makes a write callable only where a write is permitted. (3) **Validate at the earliest boundary** — every tool's arguments are parsed and validated against a strict schema (pydantic in Python, zod in TypeScript) *before* they enter the verb layer, and invalid calls are rejected with a clear structured error the model can act on. The capability-flag check belongs at this same boundary: reject a write under `read_only` before any work happens. Failing fast here is distinct from validating untrusted external input (expected uncertainty at a boundary) — it is about *unexpected* internal contract violations that indicate a bug in how the server was wired.

## Feature envy — functions belong where the data lives
A function that spends most of its time accessing another module's data and calling its methods probably belongs in that module. When a verb body is dominated by reaching into an adapter's response structure — `result.data.items[0].metrics.spend`-style navigation, or repeated `adapter.getX()`, `adapter.getY()` to feed a local calculation — ask whether the operation should live closer to the data, inside the adapter behind the port. This keeps the SDK's response shape from leaking into the verb layer. Common exceptions: Strategy and Visitor patterns that deliberately cross boundaries by design.

## Temporal coupling — expose execution order in the signature
When operations must happen in a fixed order, make that constraint impossible to violate rather than documenting it. The canonical fix: have step N return a typed value that step N+1 requires as a parameter, so the type-checker prevents out-of-order calls. The safety-critical instance for an MCP server: an irreversible action must not be callable without proof that the approval gate ran. Have the gate return an approval token the irreversible verb requires as an argument, so a comment like "call the approval gate first" becomes a type the compiler enforces — the agent literally cannot construct the call without the approval having occurred. The same shape applies to "verify the connection before exposing write tools" and any multi-phase setup enforced only by convention today.

## Encapsulate boundary conditions
Boundary calculations are easy to get wrong and easy to miss when scattered. When a boundary expression appears — a rate-limit window edge, a retry-count comparison, a pagination `offset + limit`, an `items.length - 1` — capture it in a single named constant or variable rather than repeating the arithmetic at every use site. One named variable is easier to review, reason about, and change than the same expression spread across a handler.

## Use explanatory variables
Break complex calculations into intermediate results with meaningful names. Even when an intermediate value is used only once, assigning it to a well-named constant documents what the sub-expression means — without a comment. `remaining_writes = limit - used_this_window` is clearer than scattering the subtraction through a rate-limit check. This is the simplest, cheapest form of self-documenting code.

## Implement boundaries at the inflection point
Architectural boundaries cost money to implement and cost money to leave out. Don't add them speculatively (YAGNI applies — a single-host v1 may not need the model-swap boundary), but watch for the friction that signals one is needed: two concerns changing at different rates (an adapter churning while the verb layer is stable), inability to test one thing without standing up another (a verb that can't be tested without a live upstream), or a "small" feature requiring coordinated changes across many adapters (a sign the policy logic leaked out of its seam). When that friction appears, weigh the ongoing cost of ignoring the boundary against the one-time cost of drawing it, and implement it when the former exceeds the latter. Revisit frequently; it is not a one-time decision.

## Prefer reversible decisions — minimize irreversibility
When two approaches have similar immediate trade-offs, choose the one that can be undone or evolved more cheaply. A reversible decision — an upstream hidden behind a port rather than called inline, a transport selected in config rather than hardwired, a capability tier behind a flag rather than baked into a tool — lets you course-correct as requirements clarify. The one-way door test: once this ships, how expensive is it to reverse? Token storage shape, the structured-output contract a host depends on, and the audit-log format are often the highest-stakes one-way doors — design them with an explicit migration or deprecation path from the start. This principle compounds with the product's own domain: the *server's behavior* must also prefer reversibility, which is exactly why creation is safe-by-default and irreversible actions are separately gated — a paused draft is a reversible door, a live spend is not.

For storage and contract changes that multiple running instances or multiple host versions must tolerate simultaneously, apply the **expand/contract** pattern: (1) **Expand** — add the new structure alongside the old, both in place; (2) **Migrate** — move consumers to the new structure; (3) **Contract** — remove the old once nothing reads it. Each phase deploys and verifies independently, so any running instance sees a valid shape regardless of phase — the prerequisite for evolving a tool contract without breaking a connected host.

## Keep configurable data at high levels
Constants, defaults, and configuration known at a high level of abstraction should be declared there and passed downward — not buried in low-level functions or hardcoded deep in an adapter. The runtime model, the active capability flag, per-upstream rate-limit defaults, timeout values, and OAuth scopes belong at the configuration layer and the composition root, passed inward as explicit arguments, so a reader can see what the server runs on without spelunking through adapters. Logical dependencies should be made physical: if a verb assumes an upstream tolerates a batch of 100, the adapter should expose `max_batch_size()` so the assumption is a real API, not an undocumented constraint.

Never bake environment-specific values — upstream hostnames, the runtime model id, feature flags, secrets — into the deployed artifact. Any value that differs between environments (dev/staging/prod) is injected at run time via environment variables or a config service, so the same artifact promotes through environments unchanged. This is also the mechanism of the model-swap boundary: the runtime model and harness are config, not code. Treat configuration as a first-class artifact: version the prompt files and capability-flag config, smoke-test that referenced upstreams are reachable after deploy, and never check secrets into version control.

## If it hurts, do it more frequently — bring the pain forward
When an activity is painful, the instinct is to do it less often. The correct response is the opposite: do it more often, and sooner. Running the eval harness on every prompt-file change cannot accumulate the silent reliability drift that running it monthly produces. Re-tuning tool descriptions against a new model, rehearsed early, loses its ceremony. Testing tool calls against recorded upstream fixtures continuously from day one discovers contract breaks when they are cheapest. When you dread an activity — running evals, swapping the model, exercising the rate limiter — treat that dread as a signal it contains unresolved complexity worth surfacing now.

## Build quality in — testing is not a phase
Everyone is responsible for quality all the time, not just at the end of a cycle. A test written alongside the code it verifies is cheapest and most accurate; one written weeks later transcribes the implementation rather than specifying the intent. Build tests at every level from day one — unit tests for verbs and policy with fake adapters, example-driven contract tests for the agreed tool call→result examples, and the eval harness for tool-call reliability per model. Push each test to the lowest level that can hold it, per `shared/testing-quadrants.md`. A capability is only done when it passes its acceptance criteria — its concrete call→result examples and its safety invariants (gate enforced, creation paused, mutation audited, no secret leaked) — not when the handler merely compiles.

## Cycle time is the global metric — optimize end-to-end, not locally
The most important delivery metric is **cycle time**: the elapsed time between deciding a change is needed and having it in users' hands. Secondary metrics — eval pass rate, test coverage, contract-test count — are diagnostics for investigating a cycle-time problem, not goals in themselves. Optimizing a local metric that is not the bottleneck produces no improvement and can make it worse. The lean test: "How long to get a single-line change — a tightened tool description, a new scope — from commit to a connected host, reliably and repeatably?" If that answer is measured in weeks, find the bottleneck, exploit it, then find the next one. When defects accumulate, make them visible alongside features rather than hiding them; a growing silent backlog means cycle time for bugs is too long.

## Model stable data concepts as value objects
When a concept is defined entirely by its attributes and has no meaningful identity beyond them — a spend amount, a date range, a metric, a rate-limit window, an `account_id` — model it as an immutable value type. All state is set at construction; there are no setters; operations return new values rather than mutating the receiver. A frozen dataclass in Python or a readonly type in TypeScript is the shape. Value semantics make equality straightforward, eliminate aliasing bugs, and let you reason about a value without tracing who else holds a reference — which matters when that value is an idempotency key or a spend amount flowing through the policy layer toward an irreversible action.

## Translate exceptions at architectural boundaries
When an error crosses an architectural boundary — from an adapter into the verb layer, from the verb layer into the tool handler — translate it before passing it up. A raw vendor SDK exception or an HTTP error belongs to the adapter's vocabulary; leaking it inward forces the verb layer to import SDK or HTTP types and couples it to an implementation detail. Map the low-level error to a domain error appropriate to the receiving layer, preserving the original cause for diagnostics, and map *that* to a clear structured tool error at the protocol boundary — one the model can actually act on, never a raw stack trace and never one containing a secret. Each layer then handles only the error vocabulary it owns, and the Dependency Rule stays intact.

## Design APIs with symmetry
Symmetric APIs are easier to learn and harder to misuse — for the model as much as for engineers. When you add a verb — `create`, `enable`, `start` — also provide its reversal — `delete`, `disable`, `stop` — so the model isn't stranded with a one-way action it can't undo. When several tools share an argument shape, a fourth that diverges without reason is a design flaw; investigate whether it should conform. When the same idea appears under two names (`count` vs. `size`, `fetch` vs. `load`) across adapters, pick one and apply it throughout. Inconsistency adds mental load on readers and degrades the model's tool-selection accuracy; symmetry removes it.

## Surface trade-offs explicitly
Don't bury decisions in code. A constraint, a risk, or a rejected alternative worth knowing — why a capability is deferred behind an extension hook, why an upstream is called directly rather than via its third-party server, which capability tiers v1 enables — belongs in a plan, a comment, or a handoff note, not silent in the implementation.

## Ask when uncertain
A question is cheaper than a wrong implementation — and far cheaper when the wrong implementation can spend money or take an irreversible action. If a decision is genuinely ambiguous, especially one touching a capability tier, a scope, or the safety model, surface it rather than guessing, and default toward the lower-risk path while you wait.

## Cite current documentation
When a decision rests on current behavior — an MCP spec primitive, an SDK API, a transport or auth obligation, an upstream's current capability or whether an official server for it exists — cite the authoritative source per `mcp/resources.md`. Training data is behind here, and the spec, SDKs, and vendor servers move fast; official sources take precedence over community convention and over memory.
