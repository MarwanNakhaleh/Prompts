# iOS Engineering Principles

These principles apply to every prompt in `ios/` — build-app, feature-dev, refactoring, security, and QA. They are the background framework for every architecture, implementation, and audit decision.

When making decisions that depend on current platform behavior — Swift concurrency semantics, SwiftUI lifecycle, security APIs, or any Apple framework — consult `ios/resources.md` first. It lists the authoritative, regularly-updated source for each application slice so you ground decisions in live Apple documentation rather than training-data memory.

## Simplicity is the deliverable
If two solutions work, ship the one that's easier to read and delete. Optimize for readability and the next engineer who maintains this. Unnecessary abstraction, premature generalization, and speculative flexibility are bugs.

Getting the app to work is step one ("make it work"). Step two is making it right — refactoring so the next engineer can understand and evolve it. Step three is making it fast only where actually needed. Code that only ever reaches step one accumulates coupling until it becomes unmaintainable: every change touches hardware, OS, and business logic at the same time, and the codebase can no longer outlive the platform it was written for. The simplest version that fully works *and* is easy to change is the target.

## Don't gold-plate
Solve the stated problem, not imagined future ones. The simplest version that fully works is the target.

## Names reveal intent
A name should tell you why it exists, what it does, and how it is used. If a name requires a comment to explain what it does, the name fails. Prefer `elapsedTimeInDays` over `d`, `getFlaggedCells()` over `getThem()`. Avoid noise words (`Data`, `Info`, `Manager`, `Processor`) and type encodings. Use one word per concept across the codebase — pick `fetch` or `get` or `retrieve`, not all three for equivalent operations in different classes. Class names are nouns, function names are verbs. Names at the right level of abstraction: problem-domain names where there is no programmer term, solution-domain names (patterns, algorithms) where there is. The length of a name should correlate with the size of its scope — a loop variable in a five-line closure can be `i`, but a method reachable across modules needs a precise, full name. Names must also describe everything a function does, including side effects: a function that creates an object on first call and returns it thereafter should be named `createOrReturnX`, not merely `getX` — hiding a side effect under a simple verb is a temporal-coupling trap. Extract complex boolean expressions into intent-revealing predicate functions (`if canBeCompacted()` rather than inline multi-clause expressions) and prefer positive predicates over negative ones — `canBeCompacted()` is easier to reason about than `!shouldNotBeCompacted()`.

## Functions do one thing at one level of abstraction
A function does one thing when all its steps are one level of abstraction below its name — not a mix of high-level policy and low-level detail in the same body. If you can extract another function with a name that is not merely a restatement of the implementation, the function is doing more than one thing. Flag arguments (boolean parameters) reliably signal a function doing two things: split into two clearly-named functions. Side effects that a function's name doesn't declare are temporal coupling hazards. Keep functions small enough that the intent is immediately obvious.

## Comments compensate for failure to express in code
A comment that explains *what* code does is a naming or structural failure: rename, extract a function, introduce a well-named variable. Comments lie as code evolves — they rarely follow the code they describe. Use comments only when the *why* cannot be expressed in structure: a hidden constraint, a non-obvious invariant, a workaround for an external bug, or a warning of serious consequences. Legal comments, amplification of subtle requirements, and TODOs that name a concrete next action earn their place. Comments that restate code, record history, or explain what a well-named function already says do not.

## Leave it cleaner than you found it
Every time you touch code, leave it slightly cleaner than you found it — a better name, a shorter function, a removed dead branch, a missing test added. Code does not rot in one commit; it rots because each person who touched it left it marginally worse, deciding the cleanup was someone else's problem. The reverse is equally true: a codebase improves steadily when each change leaves the touched area in better shape.

Good code is not written all at once — it is refined through many small, test-preserving steps. Large structural changes should decompose into increments where the test suite is green before and after each step. If a refactoring cannot be broken into such increments, it is either too large (split it) or it changes behavior (flag it as a separate task). "Make it work → make it right → make it fast" is a mandatory sequence, not a suggestion.

## True vs. accidental duplication
Before unifying code, confirm the duplication is real. True duplication is one concept with one reason to change — every copy must change together, always. Accidental (false) duplication is code that merely looks alike today but serves different use cases and will diverge (two screens, two flows, two roles). Unifying accidental duplication couples things that change for different reasons and is painful to unwind — flag it as *deliberately keep separate*. A wire/persistence DTO that happens to look like a domain type is the classic false positive: keep them distinct. When in doubt, let the duplication stand until the shared rule is proven.

## Simple Design — four rules in priority order
A design is simple when it (1) passes all tests, (2) contains no duplication, (3) expresses the intent of the programmer — through good names, small focused units, and clear structure — and (4) minimizes the number of classes and methods. Follow them in that order: testability first, then eliminate duplication, then maximize expressiveness, and finally minimize count. These rules work together: writing tests pushes toward smaller, more focused types; removing duplication often reveals the right abstraction; expressiveness and minimization trade off at the margin — more classes that are clearer beat fewer that obscure intent. When you can't tell whether you're done refactoring, ask: does it pass all tests? Is there still duplication? Could a reader understand the intent without a guided tour? Are there classes or methods that do no real work?

## Dependency Rule — high-level policy must not depend on low-level detail
Source-code dependencies point inward toward the domain. The UI framework (SwiftUI/UIKit), the network stack, and the persistence layer are details that should depend on your domain logic, not define it — so they stay swappable and the logic stays testable in isolation without a simulator, live server, or real store. A domain type should never import `SwiftUI`, `CoreData`, or `URLSession`, or be shaped by a `Codable` DTO or a managed object. Define a protocol/port at each boundary and push the framework/persistence detail behind it. Map wire/persistence DTOs to domain types at the boundary rather than reusing one across it.

## Don't marry the framework — frameworks and SDKs are details
A framework is a detail you use, not a foundation you marry. Keep third-party framework and SDK types and annotations out of your domain/business objects. Wrap them behind a protocol you own and confine them to an outer layer — so you can adopt, upgrade, or replace the framework without rewriting the core. Apply this to UIKit, SwiftUI, Core Data, Combine, and any third-party SDK.

## Lean on the language to hold boundaries
Use access control (`private`, `fileprivate`, `internal`) and Swift Package Manager module seams so a forbidden dependency fails to compile rather than relying on code review to catch it. Default to the tightest access level and widen only when a real cross-boundary need appears. Where the architecture depends on convention alone to keep illegal imports out, a boundary will eventually be violated under time pressure.

Note: the choice of architectural style — layered, feature-sliced, ports and adapters, component-based — becomes effectively meaningless if types are made excessively public. When every type is reachable from anywhere, all architectural styles collapse into the same flat topology regardless of how directories and modules are organized. Access visibility is what gives an architectural choice its meaning; without it, the structure is labeling, not enforcement.

## Composition root — wire once, inject inward
Construct the object graph in a single composition root (the `@main` `App` / `AppDelegate`) — the one "dirty" place allowed to know concrete types, the DI framework, and configuration. Domain logic and views receive their dependencies through protocols and never reach for a shared container, singleton, or DI framework directly. This lets the same core run unchanged under a different configuration (dev/test/prod, or a SwiftUI preview) by swapping only what the root injects. Think of the composition root as a *plugin*: you can have multiple — one for dev, one for test, one for prod, one per customer or region. The core system is never aware of which plugin is active; only the root changes.

## Resilience — assume the network and every backend can fail or stall
Put an explicit timeout on every request — a slow server is more dangerous than a down one, because it hangs the UI while a down one fails fast. Bound retries with backoff. Degrade gracefully — cached/partial content with a retry affordance beats an endless spinner. Make retried writes idempotent. Treat any locally held server entity as a possibly-stale snapshot. Decode external responses tolerantly: handle unknown enum cases with a fallback; extract only the fields you use.

When building integration tests for external services, test your application against the full range of pathological behavior — not only happy and error paths, but also: refused connections, accepted connections that are then dropped, connections that accept but never reply, responses that arrive extremely slowly, responses with unexpectedly large payloads, and responses containing garbage or malformed data. A test harness that can simulate these failure modes gives you confidence the app handles production chaos before it appears in production. Apply the **Circuit Breaker** pattern to trip and fast-fail callers when a dependency is persistently unhealthy, and the **Bulkhead** pattern to isolate failure in one integration from spreading to the rest of the app — so a third-party API going down degrades one feature, not the entire session.

## Concurrency is a separate concern
Swift concurrency (actors, `async`/`await`, structured tasks) has its own design, failure modes, and testing requirements that are fundamentally different from single-threaded code. Keep concurrency orchestration separate from domain and business logic: a domain type should not know whether it is called from a background context or the `@MainActor`. Limit the scope of shared mutable state — prefer immutable value types and copies over synchronized references. When shared state is unavoidable, define the ownership boundary explicitly with an actor, keep it narrow, and let the compiler enforce isolation. Concurrency bugs are often non-repeatable and surface only under load; the primary defense is to write domain logic in plain, `@MainActor`-free types that are testable without a running scheduler or concurrency harness, and to test concurrency behavior (task cancellation, actor isolation, retry races) explicitly and separately from domain logic. Synchronize as little as possible — keep synchronized regions as narrow as they can be; extending synchronization to an entire method when only one field access requires coordination serializes all callers unnecessarily. Prefer types that encapsulate their own thread safety (server-based locking) over patterns that require every caller to synchronize externally (client-based locking) — when a type is responsible for protecting its own state, callers cannot forget to lock it, reducing error surface and centralizing the locking policy in one place.

## Tell, don't ask — Law of Demeter
A type should only call methods on: itself, objects it creates, objects passed as arguments, and objects it holds directly as stored properties. Avoid chains that navigate through multiple layers — `a.getB().getC().doSomething()` exposes internal structure, couples the caller to every intermediate type, and means a change to any link in the chain requires updating the caller. When you find yourself navigating through an object's internals to reach what you need, tell the nearest object to perform the operation instead and let it delegate internally. If the nearest object doesn't expose that operation, add a well-named method to it rather than reaching inside.

## Return empty objects, not nil
When a query finds nothing, returning nil/Optional forces every caller to guard before using the result. Instead, return a special-case value that behaves correctly in the "nothing here" state: an empty array over nil, a zero-value struct, or a lightweight null-object type. Callers use the return value directly without defensive nil-checks, and the "not found" handling lives in one place — the returning function — rather than scattered across all callers. Reserve nil/Optional for cases where the caller genuinely needs to distinguish absence from presence and acts differently on each; for simple "nothing found" results, prefer the empty or default form. Relatedly, avoid returning sentinel error codes (−1, 0, a magic string like `"ERROR: ..."`) to signal failure. Callers cannot reliably distinguish a sentinel from a legitimate result, must remember to check it, and often don't. Use thrown errors or typed `Result<Value, Error>` types for failures and reserve return values for meaningful data.

## Feature envy — methods belong where the data lives
A method that spends most of its time accessing another type's data or calling another type's methods probably belongs in that type. When a method body is dominated by `other.getX()`, `other.getY()`, `other.getZ()` feeding a local calculation, ask whether the calculation should live inside `other` instead — and move it there. Common exceptions: Strategy and Visitor patterns deliberately cross this line when the design is intentional.

## Temporal coupling — expose execution order in the signature
When functions must be called in a fixed order, make that constraint impossible to violate rather than documenting it. The canonical fix: have step N return a value that step N+1 requires as a parameter, so the compiler rejects out-of-order calls. A comment that says "call configure() before use" is a hidden temporal coupling; a parameter type that proves configure() ran is an explicit one. Flag any type that requires multi-step initialization where the order is enforced only by convention rather than the type system.

## Encapsulate boundary conditions
Boundary calculations are easy to get wrong and easy to miss when scattered. When a boundary expression appears (e.g., `n + 1`, `last - 1`, `array.count - 1`), capture it in a single named constant or variable rather than repeating the arithmetic at every use site. One named variable is easier to review, reason about, and change than the same expression spread across a function body.

## Use explanatory variables
Break complex calculations into intermediate results with meaningful names. Even when an intermediate value is used only once, assigning it to a well-named variable documents what the sub-expression means — without a comment. `let nextLevel = currentLevel + 1` is clearer than scattering `currentLevel + 1` through the surrounding code. This is the simplest, cheapest form of self-documenting code.

## Implement boundaries at the inflection point
Architectural boundaries cost money to implement and cost money to leave out. Don't add them speculatively up front (YAGNI applies), but watch for the friction that signals one is needed: two concerns changing at different rates, inability to test one thing without spinning up another, or a "small" feature requiring coordinated changes across many unrelated areas. When that friction appears, weigh the ongoing cost of ignoring the boundary against the one-time cost of drawing it — and implement it when the former exceeds the latter. Revisit this judgment frequently; it is not a one-time decision.

## Keep configurable data at high levels
Constants, defaults, and configuration values that are known at a high level of abstraction should be declared there and passed downward as arguments — not buried in low-level functions or hardcoded deep in the implementation. When a constant lives close to where it is used but far from where it conceptually belongs, readers must search through implementation layers to understand what values the system runs on. Declare defaults and tunable values at the entry point or configuration layer, expose them as explicit arguments or injected values, and let lower-level components receive them rather than re-derive them. Logical dependencies — assumptions a module makes about another module without asking it — should be made physical: if a caller assumes a callee can handle a page size of 55, the callee should expose `maxPageSize()` so the assumption is encoded in a real API rather than an undocumented constraint.

Never bake environment-specific values — API hostnames, service URLs, feature switches, secrets — into the compiled binary. Any value that differs between environments (dev / staging / prod) must be injected at build, deploy, or run time (via xcconfig, environment variables, or a configuration service) so the same binary artifact can be promoted through environments unchanged. A binary with production endpoints baked in cannot be safely exercised in staging; a binary that receives them at run time can be verified anywhere and released with confidence.

## If it hurts, do it more frequently — bring the pain forward
When an activity is painful, the instinct is to do it less often. The correct response is the opposite: do it more often, and sooner. Integration done on every commit cannot accumulate the explosive merge debt that integration done monthly produces. Deployment rehearsed in every environment loses its ceremony. Testing deferred to the end discovers defects when they are most expensive to fix; testing continuously from day one discovers them when they are cheapest. When you find yourself dreading an activity — merging, deploying, writing tests, updating documentation — treat that dread as a signal that the activity contains unresolved complexity worth surfacing now rather than later.

## Build quality in — testing is not a phase
Everyone on a delivery team is responsible for quality all the time, not just testers, and not just at the end of a cycle. A test written alongside the code it verifies is cheapest and most accurate. A test written weeks later is often a transcription of the implementation rather than a specification of the intent — it proves the code ran, not that it was correct. Build automated tests at every level (unit, integration, acceptance) from day one. A feature is only done when it passes its acceptance criteria in a production-like environment, not when it compiles locally or when unit tests are green in isolation. Each handoff of a defect between people multiplies the cost to fix it; the cheapest fix is the one that never leaves the developer's machine.

## Cycle time is the global metric — optimize end-to-end, not locally
The most important delivery metric is **cycle time**: the elapsed time between deciding a change is needed and having that change in users' hands. Secondary metrics — test coverage percentage, defect count, build duration, velocity — are diagnostics for investigating a problem in cycle time, not goals in themselves. Optimizing a local metric that is not the bottleneck produces no improvement in cycle time and can even make it worse. The lean test: "How long would it take to get a single-line change from commit to production, reliably and repeatably?" If that answer is measured in weeks, the bottleneck is somewhere in your process — find it, exploit it, then find the next one.

When defects accumulate in a backlog, make them visible: display count, trend, and priority alongside features rather than hiding them in a separate system. A growing silent backlog is a sign that cycle time for bugs is too long, and that quality issues are not being resolved at the rate they are discovered. Bugs that are never fixed tend to be bugs nobody knows about.

## Surface trade-offs explicitly
Don't bury decisions in code. A constraint, a risk, or a rejected alternative worth knowing belongs in a comment, a plan, or a handoff note — not silent in the implementation.

## Ask when uncertain
A question is cheaper than a wrong implementation or rewrite. If a decision is genuinely ambiguous, surface it rather than guessing.

## Cite Apple documentation
When a decision rests on current platform behavior, cite the Apple developer documentation or the relevant WWDC session. Training data can be behind; first-party sources take precedence over community convention.
